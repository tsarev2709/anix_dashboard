# Месячный прогноз продаж

Экран `index.html#forecast`, компактный вариант `amo-forecast.html` и API
`GET /functions/v1/sales-forecast?month=2026-09&manager=0&pipeline=0`
используют один серверный вычислитель. amoCRM остаётся источником сделок.

## Что реализовано

- `crm_leads.expected_close_date` и флаг некорректной даты.
- Синхронизация метаданных полей и причин проигрыша через существующий OAuth.
- Выбор поля по точному названию/коду либо явно заданному реальному ID.
  Несколько совпадений, отсутствие поля или неподходящий тип дают явное предупреждение.
  При первичной настройке владелец может создать поле кнопкой в отчёте.
  Сервер дважды проверяет metadata API и блокирует одновременное создание;
  существующее подходящее поле переиспользуется. Неопределённый результат
  создания требует проверки, а не автоматического повторного POST.
- Факт по дате закрытия, сумма ожидаемых открытых сделок и взвешенный прогноз раздельно.
- Настройки вероятностей и контроля даты на экране, привязанные к парам
  реальных pipeline/status ID из ответа amoCRM. Шкала подписаний согласована 21 сентября: 50 / 70 / 80%.
- Приоритет: manual override → observed (если включено и достаточно истории) →
  настроенный fallback → неизвестно. 0% является допустимым значением.
- При отсутствии вероятности хотя бы у одной ожидаемой сделки общий weighted
  forecast равен `null`; известная часть и непокрытая сумма выводятся отдельно.
- Фильтры месяца, менеджера и воронки; расшифровка сделок, просрочки,
  следующий шаг, наблюдаемое время на стадии, качество данных и причины отказов.
- Ежедневные срезы после синхронизации, независимо от открытия страницы;
  первый срез дня сохраняется без перезаписи. Срезы строятся для текущего месяца
  и будущих месяцев с датированными сделками, в общих и раздельных разрезах.
- Новая функция проверяет пользователя через Supabase Auth и email владельца;
  таблицы настроек и срезов закрыты для anon/authenticated, RLS включён.
- Выгрузка JSON основного dashboard включает последний успешно загруженный прогноз.

## Определения и границы

- Денежные значения — суммы сделок, не банковские поступления.
- Месяц определяется в `crm_forecast_settings.timezone` (по умолчанию
  `Europe/Moscow`). Перед запуском сверить с timezone аккаунта amoCRM.
- При выборе прошлого месяца факт берётся из текущего состояния выигранных
  сделок; открытые сделки и дисциплина всегда отражают текущее состояние.
  Для прошлых оценок используется история snapshots, а не реконструкция.
- Conversion = won / (won + lost) по закрытым в месяце, не когортная конверсия.
- Observed probability = доля побед среди уникальных завершённых сделок,
  для которых есть посещение стадии до закрытия. Повторные посещения не
  увеличивают sample. Открытые сделки исключены, история до подключения
  интеграции неизвестна. Это может смещать оценку, поэтому модель выключена
  по умолчанию. Минимальный sample — 30; ограничение схемы — не менее 10.
- Правила подписаний настраивают required_statuses поля в amoCRM.
  Флажок «Нужна дата» отдельно включает проверку в аналитике.
- Сырые события CRM отделены от действий продавца. Ориентир — 800 действий
  на человека в день. Автоматические изменения полей и импорт не включаются.
- Выполненные задачи считаются по task_completed, а не updated_at. Это
  отдельная метрика: задача «позвонить» не доказывает звонок. Встречи и КП
  не считаются действиями автоматически по смене стадии.
- Время на стадии — по наблюдаемым переходам; до начала синхронизации неизвестно.
- Backend постранично читает таблицы и отказывается выдавать неполную выборку.
  Расчёт in-memory подходит текущему масштабу; при росте истории вынести
  агрегацию в SQL, не увеличивать лимиты молча.
- Текущая синхронизация обновляет таблицы пакетами, а не транзакцией целого
  аккаунта. Запрос одновременно с sync может увидеть промежуточное состояние.
  Snapshots запускаются после загрузки всех сущностей. Эта итерация не меняет
  существующую обработку удалённых сущностей и полноту истории до первого sync.

## Запуск

1. Получить доступ на запись к `tsarev2709/anix_dashboard`, отправить локальную
   ветку `agent/monthly-sales-forecast`, открыть PR. По существующему workflow
   доверенные `agent/*` PR могут автоматически слиться после успешной проверки.
2. CI: Node.js 24, синтаксис JS, `node --test tests/*.test.mjs`, сборка статики.
3. После merge проверить `Deploy Supabase`: новая миграция включена в список
   идемпотентных миграций, затем деплой всех функций и 401 для анонимного доступа.
4. Дождаться успешного `Sync amoCRM` (по расписанию каждые 30 минут) и посмотреть
   поле `expectedCloseField` в его ответе. Поле даты создаётся отдельным действием
   владельца; первый sync после миграции правил подписаний может создать поле
   формата контракта и настроить обязательность даты (см. ниже).
5. Проверить полученные метаданные:

   ```sql
   select external_id, name, code, field_type, synced_at
   from public.crm_lead_custom_fields where source_slug = 'amocrm';
   select source_slug, expected_close_field_id, timezone, field_state, metadata_synced_at
   from public.crm_forecast_settings where source_slug = 'amocrm';
   ```

   Если аналог есть — выбрать его фактический ID в
   `crm_forecast_settings.expected_close_field_id` через защищённый SQL-доступ.
   Если аналога нет — кнопка «Добавить дату сделки в amoCRM» в отчёте создаёт
   поле типа **Дата** с названием **Потенциальная дата сделки**. Затем ещё один sync.
6. Проверить реальные стадии в блоке настроек, согласовать вероятности и
   стадии обязательности даты, сохранить. Не переносить шкалу процентов из
   handoff без проверки. Observed включать через защищённую настройку только
   после проверки качества истории.
7. Сверить 3–5 сделок: сумма, стадия, ожидаемая дата, ответственный, следующий
   шаг; вручную пересчитать факт/weighted/nominal выбранного месяца.
8. Проверить desktop/mobile, фильтры, ссылки на сделки, ошибки auth и sync,
   появление среза в `sales_forecast_snapshots`.

## Компактная страница внутри amoCRM

Адрес после публикации: `https://dashboard.anix-ai.pro/amo-forecast.html`.
Использует тот же Supabase login; токены не помещаются в URL или postMessage.
При запрете sessionStorage вход работает в памяти до перезагрузки страницы.

21 сентября 2026 страница добавлена через «Настроить» → «Добавить свой виджет»
на рабочем столе владельца в amoCRM, размер 4 × 4, в нижней части рабочего стола.
Настройка не применялась ко всем пользователям. Проверены сохранение виджета
после повторного открытия CRM, вход через iframe и загрузка реального отчёта.
Число и сумма сделок без даты совпали с независимой проверкой базы данных.
Для доступа по-прежнему требуется отдельный вход владельца в Anix;
авторизация в amoCRM его не заменяет. Публичного endpoint с данными нет.

`frame-ancestors` действует только в HTTP-заголовке, его нельзя надёжно задать
в meta-теге на GitHub Pages. При необходимости настроить на прокси хостинга:
`Content-Security-Policy: frame-ancestors 'self' https://studioanixaipro.amocrm.ru`.
Не считать интеграцию завершённой без проверки внутри amoCRM.

## Проверки этой ветки

Локально: тесты расчётов, метаданных, постраничной загрузки и безопасного
создания поля; синтаксис JavaScript и TypeScript. Первый релиз прошёл GitHub
Actions, миграция и функции опубликованы. Вход владельца и чтение реального
отчёта в production проверены. Встраивание, вход и чтение данных внутри amoCRM
проверены 21 сентября. На полном экране проверены загрузка, блок действий
продавца и фильтр сотрудника; показатели квалифицированных сделок сверены
с независимым SQL-запросом. Релиз правил подписаний (PR #16) прошёл 35 тестов,
проверки CI, публикацию статики и Supabase. Повторная синхронизация после
сетевого сбоя завершилась успешно; data_sources.status = healthy.

Первый срез 21 сентября был сделан до публикации правил и остаётся моделью 1.
Он намеренно не перезаписан; модель 2 появится при первом успешном срезе
следующего дня. Наличие дневного среза само по себе не доказывает его модель.

Осталось: заполнить реальные даты и форматы в квалифицированных сделках,
сопоставить стадии подписаний остальных воронок по фактическому процессу,
проверить отображение на реальном мобильном устройстве.
Историческую полноту действий продавцов нельзя подтвердить текущим набором
событий; поиск и исследование требуют явно отмеченных выполненных задач.
Расчёт помесячных оплат и юнит-экономики в эту реализацию не входит.

Первый ежедневный snapshot выявил лимит ресурсов Edge Function. Создание
срезов теперь пропускает загрузку событий и расчёт ненужных детализаций,
использует один расчёт вероятностей для всех разрезов. Форматтер дат
переиспользуется. Тест сравнивает срезы с полным отчётом во всех разрезах.

Документация API:
- [Поля: типы и значения](https://www.amocrm.ru/developers/content/crm_platform/custom-fields)
- [Воронки и системные статусы](https://www.amocrm.ru/developers/content/crm_platform/leads_pipelines)

142/143 — документированные системные статусы amoCRM, не предположения об
этапах аккаунта. Вероятности пользовательских стадий определяются по их
реальным идентификаторам, полученным API.

## Уточнения после подключения Supabase

Проверена структура production и действующая версия amocrm-sync: исходная
версия функции соответствует main. Forecast-таблицы развёрнуты.
Неиспользуемое поле «срок» не считается ожидаемой датой закрытия и не меняется.
Полный запрос metadata API подтвердил отсутствие поля ожидаемой даты
закрытия; setup повторно проверяет список непосредственно перед созданием.

Открытые карточки включают импортированную базу поиска контактов. UI явно
отличает это количество от числа переговоров. Для факта используется только
стандартный бюджет сделки, отдельное пользовательское поле «бюджет» не
подставляется автоматически. При незаполненных суммах результат отражает
качество CRM, а не фактическую выручку бизнеса.

Историческая модель оставлена выключенной: выборка побед недостаточна для
калибровки поздних стадий. Ежедневный snapshot теперь отмечает завершение всех
месяцев/разрезов; повторные sync в этот день не загружают историю заново.
Полные повторные попытки после частичного сбоя сохраняются.

## Правила подписаний, согласованные 21 сентября 2026

В основной воронке используются проверенные реальные пары ID/название:

| Стадия | Вес | Дата |
| --- | --- | --- |
| Встреча проведена (SQL) | 50% | обязательна |
| Готовим ПКП/ТКП | 50% | обязательна |
| ПКП/ТКП отправлено | 70% | обязательна |
| Согласование условий | 70% | обязательна |
| Договор / Счёт | 80% | обязательна |

Ранние стадии, предоплата, производство и постоплата исключены независимо
от наличия суммы, даты или ручной вероятности. Непроверенные стадии других
воронок тоже исключены с предупреждением; они не считаются прошедшими встречу
только по порядку расположения воронки. Потенциальная дата означает ожидаемое
подписание договора, не срок производства. Суммы квалифицированных сделок без
даты показываются как нераспределённые по месяцам, дата не угадывается.

Первый sync после миграции однократно применяет согласованную политику через
существующий OAuth: проверяет актуальные стадии, создаёт или переиспользует
«Формат контракта», настраивает required_statuses даты начиная с встречи,
проверяет ответ API и сохраняет настройки. Повторный sync не сбрасывает ручные
настройки. Требования других воронок сохраняются. При неоднозначном создании
поля повторный POST блокируется до проверки; значения сделок не изменяются.

Формат контракта: «Разовый проект», «Регулярный ежемесячный»,
«Рамочный / нерегулярный». Незаполненное поле не считается разовым контрактом.
В отчёте группируется стандартная сумма сделки; поле не создаёт график платежей,
не умножает бюджет на месяцы и не подменяет расчёт юнит-экономики. Для последнего
потребуются отдельно период производства, помесячная загрузка команды и оплаты.

Действия: исходящие звонки, письма, сообщения и SMS с известным автором,
плюс завершённые задачи с префиксами [Поиск контакта], [Анализ сегмента],
[Анализ компании]. Задачи поиска и анализа — один результат работы на задачу.
Задачи и записи с позднее изменённым текстом не классифицируются задним числом.
Завершённые задачи показываются отдельно и не прибавляются к касаниям.
Заметки также не прибавляются к касаниям.
Повторные события одного сообщения/звонка и завершения одной задачи исключаются.
Фильтр менеджера использует автора события; фильтр воронки — связанную сделку.
События без автора не присваиваются менеджеру; без сделки не входят в разрез
воронки. Нулевая наблюдаемая активность не доказывает отсутствие работы.
Нерабочие дни не размечены: KPI за весь месяц не вычисляется.

История до подключения интеграций неполная. Sync дополнительно читает исходящие
коммуникации на контактах/компаниях с момента инкрементальной синхронизации,
но это не восстанавливает прошлые телефонные разговоры или внешние чаты.
Срезы модели 1 сохраняются неизменными; новые срезы помечены моделью 2.
